## Oracle reading — confirmed, with qualifications

1. **InputXML → Categorised:** The converter groups elements by line and creates generated Line/Element/derived blocks. It embeds each *trimmed* original PIPINGELEMENT string in OriginalElement CDATA. It does **not** automatically embed OriginalDocument. Original root/header/top-level sections outside elements are lost; lexical nested CDATA is split, not guaranteed reversible. See S4-F-SOURCE and S4-F-*.
2. **Categorised → InputXML:** If OriginalDocument exists, the converter extracts its CDATA and returns that source string directly, ignoring derived edits; this is an identity bypass, not a patch. Its regex is NOT lossless for a nested original CDATA terminator. Otherwise it joins OriginalElement strings and extracted external node blocks under a **new** CAESARII/PIPINGMODEL wrapper, dropping the source header and nonexternal sections. Edited derived Material/Geometry values silently disappear. See S4-D-*, S4-N-* and S4-N-DERIVED.
3. **Enriched** is a marker flag independently reported alongside format kind (xml / inputxml / categorizedxml / unknown), not another XML format. See S4-ENRICH-DETECT.

## Workspace stages, markers, and formatting

The Workspace stages are **1 CleanXML**, **2 InputXML Enrichment (apply sideload)**, **3 XML→InputXML 5C (handoff into Tab 2)**, and **4 Categorized XML**. Tab 2 calls applyXmlCompareSideload, not the separate standalone XMLSerializer-based enrichment function. Stage 1 constructs a CleanXML node/branch projection from tables; Stage 3 produces/forwards an InputXML artifact and has no inherent marker insertion; Stage 4 derives a categorized display/projection with OriginalElement snapshots. The tests S4-STAGES, 18 S4-MARKER-STAGE1/2 cases, S4-STAGE3-5C-HANDOFF and S4-STAGE4-CATEGORIZED distinguish these roles.

| Marker | Stage 1 CleanXML | Stage 2 actual sideload | Stage 3 5C handoff | Stage 4 categorize |
|---|---|---|---|---|
| PipingClass | Can add tag from table | Keeps existing; **not created** | Carries supplied InputXML; no mutation in handoff | May derive from LINE_ID |
| Rating | Can add tag from table | Keeps existing; not created | No mutation in handoff | May derive from class |
| DTXR_POS | Can add node tag | Keeps existing; not created | No mutation in handoff | Carrier retains original if present |
| DTXR_PS | Can add node tag | Keeps existing; not created | No mutation in handoff | Carrier retains original if present |
| MaterialNumber | Can add branch tag | Keeps existing; not created | No mutation in handoff | MATERIAL_NUM may be projected; not native update |
| MaterialName | Can add branch/node tag | Keeps existing; not created | No mutation in handoff | Derived MaterialName if source has MATERIAL_NAME |
| LINE_ID | No InputXML attribute; branch/node context | **Add or replace attribute** from sideload | Carries source attribute if present | Line grouping and OriginalElement |
| FROM_NAME | CleanXML NodeName, not InputXML attr | **Add or replace attribute** | Carries source attribute if present | NameBlock and OriginalElement |
| TO_NAME | CleanXML NodeName, not InputXML attr | **Add or replace attribute** | Carries source attribute if present | NameBlock and OriginalElement |

**Does Stage 2 only add fields? NO.** It also **replaces** matched LINE_ID, FROM_NAME, TO_NAME values and restraint TAG, may append FROM_GLOBAL/TO_GLOBAL XYZ plus basis-node attributes from coordinate sideload, and can change the quote style of an edited attribute (single quotes become double quotes). Existing attribute order is generally retained, but newly added attributes append and edited opening-tag bytes change; unlike the standalone DOM serializer, the actual Workspace sideload ordinarily preserves unmatched body, root, comments and document spacing as-is. No-match sideload returns the input identical. Proved by S4-STAGE2-ATTRVALUES, S4-STAGE2-UNCHANGED, S4-STAGE2-FORMAT, S4-STAGE2-OTHER-SOURCE-ATTR, S4-STAGE2-PUBLIC. 5C handoff rejects zero or non-InputXML results (S4-STAGE3-5C-HANDOFF refusal case). The enriched flag is *independent of* this schema kind (S4-ENRICH-DETECT).

## Multi-branch categorizedExternalBlocks

The compatibility code globally finds RESTRAINT, DISPLACEMENTS and FORCESMOMENTS raw stanzas within the whole categorized string (even within copied OriginalElement CDATA text), checks active values and deduplicates by **trimmed lexical string**, not by source record/branch. With synthetic three elements on two line groups, two identical R1 restraints and one R2 produce **two unique external stanzas**. Without OriginalDocument, the reverse output contains **three R1 occurrences** (two in copied originals + one external) and **two R2 occurrences** (one original + one external): it can duplicate source semantics. The test S4-EXT-MULTIBRANCH proves this and grouping. This is not source-preserving normalization.

## S4.1 / S4.2 can rely on — bounded facts

1. S4.1 may read categorized Line/Element/derived blocks as **reviewable evidence**, and OriginalElement as a **trimmed source snapshot**. It cannot treat derived changes as edits already committed into an original InputXML file.
2. S4.1 must reconcile valid original sourceRefs (format, exact fileSha256, recordKey), provenance, loss/duplicate external witnesses and unknown header/sections independently; a missing OriginalDocument or nested CDATA case is NOT proof of source equivalence. XCU stays D1 canonical UXML authority.
3. S4.2 must patch the **original InputXML bytes** using verified sourceRefs and existing safety policy, preserving untouched records, root, header, comments, BOM/EOL, ordering and nonexternal sections; or refuse without a file. Never use the compatibility reverse converter as the patch writer.
4. An edited derived value, duplicated external block, missing source field or failed original-byte parity needs **explicit engineering review/HOLD**; no silent rebuild, allow-list or invented authority.
5. Treat enriched as marker metadata, **not another input file format**.
